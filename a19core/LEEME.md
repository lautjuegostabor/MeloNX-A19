# A19Core Modular 1.1 — fuente de integración, sin compilar

Base: MeloNX commit `f925129209afd55927a0201d82285b8fa4b7ba30`, overlay SHA-256 `dfd0e7c1bde9029aec5c2d2347086a15342995da135fec54842587796e04400f`, parches review, lab, v05 y v06 del workflow funcional. No se utiliza v07 R3 ni S2Arm como núcleo. La compilación manual futura conserva el runner xcode-27 y el flujo v0.6; `a19-build.yml` es una copia local, no se publicó. Requiere el overlay original en el repositorio, la revisión base y las dependencias externas del build. No incluye IPA, juegos, keys ni firmware.

Se mantienen los cinco switches de v0.6 (bits 1–16) y cuatro selectores existentes. No habilitar todos juntos. El menú Performance Lab guarda de forma atómica la configuración en Documents/A19Core-options.json y restaura los valores al relanzar la app. El botón funciona también durante una captura y guarda opciones para el próximo juego sin modificar el núcleo activo. Antes de iniciar, se guarda la selección actual, se transmite al núcleo y se exige lectura de retorno exacta de los cuatro selectores y la máscara de 17 bits. Si no coincide, se cancela el inicio con un error visible. Restablecer referencia guarda todos los valores en cero; también se restaura el límite original de command buffers y la configuración de métricas de MoltenVK cuando se vuelve a Original. El JSON de sesión registra trialConfigReadback=verified al comenzar una prueba con captura. Las métricas son acumuladas, no tiempos de pared; guardar ambos JSON/JSONL inmediatamente después de cada prueba pues conservan los nombres originales. Los contadores de actividad no demuestran mejora. Con las opciones desactivadas se conserva la ruta funcional de v0.6, pero no se afirma equivalencia binaria o de rendimiento.

## Modular 1.2 — diagnóstico automático (sustituye el comportamiento de captura y Aplicar descrito arriba)

- Al iniciar una partida, si la opción Diagnóstico automático está activada (por defecto), crea `Documents/A19Core-Diagnostics/<UTC>-<UUID>.jsonl`. El JSONL contiene cabecera con 171 nombres, índices absolutos, frecuencia de Stopwatch, contexto del juego, hardware, selección guardada y selección aceptada, muestras y footer en cierre normal. La UI permite compartir el último JSONL tras finalizar. Tras relanzar, recupera el más reciente. Conserva las diez últimas sesiones de ese directorio; también se puede acceder a sesiones anteriores desde Archivos si la configuración de exposición de Documents de iOS lo permite.
- Writer nativo dedicado, objetivo de 250 ms entre muestras, máximo 2401 muestras (~10 minutos si el muestreo cumple el objetivo); `fflush` por muestra y `fsync` al cambiar de fase, cada cuatro muestras y al finalizar. Un cierre abrupto puede perder las últimas muestras, no genera un stack trace; si falta el footer no se puede distinguir cierre forzado, jetsam o crash solo con JSONL. No se instala un handler de señales ni se escribe desde uno. No recopila contenido del juego, rutas, claves, pairing, ni mensajes de log sin filtrar. Incluye title ID y versión del juego.
- `phase`: 0 preparación, 1 lanzamiento/juego activo, 2 retorno del núcleo. `exitCode` solo es interpretable cuando phase=2. Footer reason 0 parada, 1 límite de muestras, 2 error del writer. Si se alcanza el límite o se detiene antes de salir, no se registrará la salida posterior. `previousSampleCostMs` incluye lectura de contadores, CPU/memoria, formato y escritura de la muestra previa. CPU es tiempo de proceso acumulado; memoria es footprint y disponibilidad de proceso, no RAM libre del dispositivo. Footprint=0 es no disponible. Temperatura es estado térmico del último muestreo desde Swift, no grados ni lectura independiente de UI; si la UI se bloquea puede quedar desactualizada.
- Histogramas disjuntos de intervalos entre presentaciones guest: los nombres `frame_hist_le_*` representan el intervalo entre el límite anterior y el límite indicado, no histogramas acumulados por umbral. p50/p95/p99 se estiman como rangos de bins, no percentiles exactos. Primer y último evento de presentación guest y primer host reportado se expresan en ticks Stopwatch. No son scanout de pantalla. `sample_stopwatch_ticks` usa el mismo reloj que los eventos.
- Ocho etapas: JIT, espera de fence de command buffer, llamada a QueueSubmit, creación de pipeline Vulkan, trabajo de compilación en background, asignación Vulkan, llamada a PresentLoop y adquisición del mutex de creación de pipelines. Cada una registra inicios, operaciones en curso, máximos, número de duraciones >=16ms, último fin/duración lenta aproximados. La pareja último fin/duración puede no corresponder a una sola operación si hay escritores concurrentes; no es un ring de eventos ni identifica cada llamada individual. El tiempo concurrente se superpone. La espera de mutex de pipeline se mide separadamente de su llamada Vulkan; no todos los locks, fences o compiladores están instrumentados. Los contadores se reinician al activar una nueva captura antes de iniciar el motor; las colecciones GC son acumuladas de proceso. Se agregan cola de compilación, pool experimental retenido, memoria managed estimada, warnings/errors numéricos, código Vulkan de último error de pipeline y ausencia de tipo de memoria adecuado. Los gauges de MoltenVK se leen en su ruta existente y se marcan no inicializados hasta que hay lectura.
- Se mantiene la separación de opciones: los cambios sin Aplicar nunca se guardan al iniciar. Si falla la aceptación de configuración, se intenta referencia; si incluso esta es rechazada, se evita iniciar con estado desconocido. Un fallo de captura no impide jugar. La confirmación sigue siendo recepción de configuración; la actividad real se observa en contadores, no se promete aprobación individual por cada subsistema. Los pools previos no se purgan globalmente: cerrar completamente la app entre pruebas cuando se quiera reducir contaminación de memoria. La caché persistente de shaders no se elimina. La captura puede alterar tiempos y activar tracking MoltenVK, por lo que comparar siempre capturas con la misma opción de diagnóstico; se puede desactivar para jugar.
- `analyze_trace.py` es una herramienta local opcional de análisis, no se instala en el iPhone. Lee esquema 5, calcula rangos de percentiles y ventanas de tirones, actividad de opciones, máximos y memoria; tolera última línea incompleta. Validada con datos sintéticos, no con resultados del A19. El usuario solo necesita compartir el JSONL. Si el proceso desaparece, compartir también el `.ips` de iOS correspondiente si existe. El informe JSON adicional es opcional y no contiene la serie de muestras.
- Verificaciones: parseo sintáctico Swift (sin SDK iOS), `clang -fsyntax-only` del código C en Linux (no valida rama Apple), correspondencia exacta de cabecera C y nombres Swift/C# (171), análisis sintético con línea truncada, aplicación/reversión del parche contra base v0.6 y coincidencia byte a byte de todos los archivos modificados; YAML del workflow parseado y parche incrustado idéntico. No se compiló, enlazó ni ejecutó el emulador. No se modificó GitHub. No se ha medido el sobrecoste de diagnóstico en iPhone.

## Modular 1.3 — rendimiento gráfico (sustituye la descripción de pipelines y diagnóstico anterior)

Revisión de los dos registros reales del usuario: cerca del segundo 75, referencia 27.502 llamadas QueueSubmit, 12,17 s acumulados, 1.841 pipelines y 10,56 s acumulados; con máscara 131040: 30.840 llamadas, 14,00 s, 1.814 pipelines y 9,81 s. Las escenas no están controladas, los estados térmicos iniciales son distintos y el shader cache estaba desactivado. No se afirma causalidad ni mejora de FPS.

- Las opciones existentes de búsqueda de buffers, uniforms y GPFIFO usan lotes de 256 aciertos locales por hilo para publicar al contador global. El residuo no se publica; son cotas inferiores, no recuentos exactos. El epoch descarta los residuos de sesiones anteriores; se mantiene la precondición anterior de no arrancar una captura nueva con el motor anterior activo. Los otros contadores conservan su semántica. La disminución de operaciones atómicas es aritmética, no un benchmark A19.
- Bit 16384: cambia de pipelines sin caché a concurrentes con caché compartida. El pipeline cache de PipelineBase se crea sin EXTERNALLY_SYNCHRONIZED y Vulkan permite sincronización interna de estas llamadas. Se conserva la ruta original bajo mutex al desactivar la opción y la espera de compilaciones de ShaderCollection antes de destruir la caché. No se garantiza ausencia de contención interna en MoltenVK. Referencia: https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateGraphicsPipelines.html y https://docs.vulkan.org/refpages/latest/refpages/source/vkCreatePipelineCache.html.
- Bit 131072 (nuevo, desactivado en referencia): agrupar envíos de GPU. Únicamente difiere la decisión heurística de flush por cambio de attachments cuando han pasado entre 1 y 2 ms desde el anterior flush, no hay queries pendientes ni fast flush mode y la disponibilidad de memoria del proceso (muestreada, puede estar retrasada) es de al menos 768 MiB. No modifica barreras, syncpoints, query flush, peso de recursos, ni presentación. No es una garantía de latencia máxima de GPU; se prueba como opción independiente. Los umbrales son experimentales, no valores medidos como óptimos en A19.
- GPFIFO: conserva el mismo tope de 128 entradas por procesador y requisitos de igualdad exacta. Al alcanzar el límite, expulsa una entrada FIFO en lugar de vaciar el diccionario completo. Se añade una cola acotada y counters de admisiones y expulsiones. No modifica interpretación ni comandos ejecutados.
- Esquema 6, 175 contadores. El 76 pasa a a19_shared_pipeline_calls; 171–174 registran decisiones de flush, admisiones y expulsiones GPFIFO. Analizador compatible con esquemas 5 y 6. Los logs siguen guardándose automáticamente. Restablecer referencia después de instalar: los bits antiguos pueden persistir y el bit 16384 ha cambiado de semántica.
- Pruebas sugeridas: misma partida/escena, 75 s desde el arranque, resolución y caché idénticas, empezar con temperatura nominal; primero referencia, después solamente Agrupar envíos GPU, luego solamente Pipelines concurrentes con caché compartida. Mantener diagnóstico automático. Los cambios de GPFIFO y contadores se aplican al activar sus opciones existentes. No se modificó el ciclo de cierre.
- Validación: aplicación y reversión del delta sobre el árbol 1.2, parseo Swift, sintaxis C Linux, correspondencia de los 175 nombres C/Swift/schema, workflow YAML y parche incrustado exactos, lectura de los dos JSONL reales con el nuevo analizador. No se compiló C#, no se enlazó con iOS y no se midió rendimiento de los cambios. El workflow incluido es local y está preparado con clave de caché del núcleo distinta.
